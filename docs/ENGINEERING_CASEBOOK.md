## 案例 1 · 并发锁竞态:check-then-act(TOCTOU)+ 启发式判据的时间窗

**发作**(2026-08-08,EXPLORATION_LOG E1):用户连续两次点击运行
deepseek 任务,两个运行进程重叠 18 秒同时执行——单实例锁形同虚设。

**根因链**:
1. 完成判定采用"产物优先"启发式(踩坑 #3 引入:僵尸进程骗过
   `os.kill(pid,0)`,于是改为"该任务最新 run 目录出现 report.json
   即完成");
2. 但点击运行后有 30-40 秒预检窗口(准入门 + 模型预检),此时本次
   run 目录**尚未创建**;
3. 窗口内查询"该任务最新目录"命中的是**上一次已完成运行**(有
   report.json)→ 判"已完成"→ 锁被视为过期 → 第二次启动被放行;
4. 锁的检查(active_run)与获取(write lock)本身也是两步非原子
   操作(check-then-act)。

**这是哪类经典问题**:
- **TOCTOU / check-then-act 竞态**:检查与动作之间状态可变——文件
  存在性检查后再创建、余额检查后再扣款、库存检查后再下单,同族;
- **启发式判据缺少"本轮"锚点**:用全局可见的旧产物回答"本次是否
  完成",相当于用历史数据回答现在的问题。

**本项目修法**(commit `c8c85b7`,测试钉死):
- 锁文件写入 `started_at`(启动时刻,YYYYMMDD-HHMMSS);
- 完成判定加时间窗约束:产物目录的尾缀时间戳 **不早于 started_at**
  才算本次产物;旧产物一律不作数;
- 旧式锁(无 started_at)保持兼容语义,行为有测试固定。

**业界通用方案对照**(面试可展开):
| 方案 | 适用 | 备注 |
|---|---|---|
| `open(O_CREAT\|O_EXCL)` 原子创建锁文件 | 单机文件锁 | 把 check+act 合成一个原子系统调用,治本 |
| `flock`/`fcntl` 建议锁 | 单机进程互斥 | 进程退出自动释放,免清理 |
| 数据库唯一约束/`INSERT ... ON CONFLICT` | 有 DB 的任务队列 | 把互斥交给 DB 的原子性 |
| 分布式锁 + fencing token(Redis/ZK) | 多机 | token 单调递增防"旧持有者复活"——与本案 started_at 思想同源 |
| 乐观并发(版本号 CAS) | 高读低冲突 | 冲突时重试而非阻塞 |
本项目选 started_at 时间窗而非重写为 O_EXCL:改动最小、与既有
"产物优先"语义兼容、且窗口问题的本质是判据缺锚点而非创建不原子
(创建竞态窗口仅毫秒级,判据窗口长达 40 秒——先修大的)。

**测试与指标**:
- 回归测试 `test_lock_race_window_closed_by_started_at`:新锁 +
  存活 pid + 旧产物 → 判"仍在运行"、并发启动被拒;旧锁兼容路径
  同测钉死;
- 指标:重叠启动复现 = 修复前 1 次真实发作 / 修复后不可复现
  (时间窗判据下,旧产物无法再冒充本次完成)。

**通用教训**:任何"用可观察产物推断状态"的启发式,必须绑定本轮
的时间/身份锚点;凡 check-then-act,先问一句"这两步之间世界会不
会变"。

## 案例 2 · 静默故障转移 + 配置棘轮:开发环境"模型降级"四天不愈

**发作**(2026-08-08 至 08-11):协作模型 Fable 5 在会话中途"变笨"
并切到 Opus 5,用户四天里手敲 24 次 `/model claude-fable-5` 掰回,
每次都复发。前两轮定性全错——我先推断"配额耗尽"(用户反驳:单会话、
消耗不大),再推断"用户级 settings 的 `opus[1m]` 默认值",都是**没查
日志的推理**。第三轮改用 transcript 结构化取证,一次锁死。

**取证**(`~/.claude/projects/<proj>/*.jsonl`,jq 打结构而非 grep 正文):
- **19 次**降级事件,全部携带同一条 system 记录:*"Fable 5's
  safeguards flagged this message … Switched to Opus 5"*(其中 2 次
  切到 Opus 4.8);按日 6/7/2/4;两种措辞变体 13:6(前者明示"可能误伤
  正当的 coding、cybersecurity 任务");
- 每次切换在 transcript 里留有结构化内容块
  `{"type":"fallback","from":{"model":"claude-fable-5"},"to":{"model":"claude-opus-5"}}`;
- 切换时刻的上下文规模:392k / 418k / 496k / 634k / 679k / 780k /
  792k / 865k / 938k —— **无阈值**;而 Fable 自身最高跑到 **938,435
  tokens** 仍正常出活 → **窗口容量假说被反证**;
- 用户 `/model` 命令 24 次,时间戳普遍落在自动切换**之后 18-45 秒**
  → 人工修复循环,确认切换非用户发起。

**根因链**(三段必须拆开,只治一段都不愈):
1. **触发**=Anthropic 安全分类器命中本项目消息。本项目正是"对抗式
   harness":沙箱逃逸、护栏绕过、provenance 伪造、负控样本、越权写
   ——词汇与代码形态天然落在分类器明示会误伤的 coding/cybersecurity
   区间。**与用量、时长、窗口全都无关,是内容触发**;
2. **动作**=客户端 `switchModelsOnFlag`(默认 true)命中即**静默换模**
   继续对话。用户只能观察到二阶效应("变笨"),一阶信号是一闪而过的
   系统提示;
3. **传播**=换模结果被**写回持久配置**(用户级 `settings.json` 变成
   `"model":"opus[1m]"`)→ 此后每个**新会话**(含压缩后的新壳)出生
   即 Opus。`/model` 只医当前会话 → 形成单向**棘轮**,人工修复永远
   追不上。

**放大器(非根因,但决定痛感)**:主循环每轮重发全量 transcript,单会话
累计输入最高 **4.74 亿 tokens / 1174 轮**(均值约 40 万 tokens/轮)。
会话越长,单请求承载的可疑内容面越大、代价越高——命中概率与单次成本
同向上升。

**这是哪类经典问题**:
- **静默故障转移(silent failover)**:控制面自认"优雅降级",数据面
  质量下降却对上层不可见。同族:读写分离静默读到陈旧从库、熔断器
  fallback 掩盖真实错误率、TLS/协议降级;
- **状态棘轮 / 降级态写回(write-back of degraded state)**:本应
  单次生效的临时决策改写了持久配置,变成新默认值 → 不可逆,恢复只能
  人工。同族:feature flag 自动回滚写回默认、autoscaling 缩容不回弹、
  DNS/缓存污染;
- **可观测性缺口**:现象与信号在不同层,且信号是瞬时 UI 提示而非
  可查询记录 —— 但**结构化日志里其实全都有**(见"取证方法"教训)。

**本项目修法**(项目级 `.claude/settings.local.json`,四键各治一段):
| 键 | 治哪一段 | 语义 |
|---|---|---|
| `switchModelsOnFlag: false` | **动作** | 旗标命中不再静默换模,改为该发可见失败 → fail-fast 取代 silent fallback |
| `fallbackModel: ["claude-fable-5"]` | **动作** | 过载回退目标 = 自身(no-op fallback),不借机降质 |
| `model: "claude-fable-5"` | **传播** | 声明期望态,压过被写回的默认值 → 掐断棘轮 |
| `autoCompactWindow: 150000` (+`autoCompactEnabled`/`precomputeCompaction`) | **放大器** | 15 万 tokens 自动换壳,压住平方级重发 |

配套 `.claude/settings.json` 的 **SessionStart 钩子**注入磁盘简报
(近 3 提交 / runs 末发 / 最新预注册 / 最新状态条目,~370 tokens)=
每次冷启动做一次**配置与进度对账**,防新壳凭失真摘要办事。

**业界通用方案对照**(面试可展开):
| 方案 | 适用 | 备注 |
|---|---|---|
| fail-fast 替代 silent fallback | 质量敏感链路 | 本项目所取:宁可可见地失败,不要不可见地变差 |
| 无状态降级(决策只影响本次请求,绝不写回配置) | 一切自动降级 | 治棘轮的**根本**修法;本案是反面教材 |
| 声明式期望态 + 漂移检测(GitOps/Terraform drift) | 配置漂移 | 项目级 pin = 期望态;SessionStart 钩子 = 每次开工对账 |
| 降级事件转一阶信号(告警/计数器/SLO burn) | SRE | 把"变笨"变成可计数事件——本案的 19 次全在日志里躺了四天没人查 |
| 同质回退池(回退目标不降质) | 多 provider 路由 | `fallbackModel` 指回自身即最小实现 |

**测试与指标**(可证伪判据,非感觉):
- 主判据:新会话是否**出生即 Fable**;
- 计数指标:transcript 中 `{"type":"fallback"}` 事件数与
  `safeguards` system 条目数——修复前 4 天 **19 次自动换模 + 24 次
  人工 `/model`**,修复后目标 = 自动换模 **0**(旗标改为可见失败);
- 取证命令入库(一行 jq,见 LESSONS #19),复发时 30 秒内可复验;
- 诚实边界:若降级由服务端在配置层之上强制,配置拦不住——判据仍是
  "新会话是否生于 Opus"。

**通用教训**:"降级"一词在本案指**三件不同的事**——触发(分类器命中)、
动作(换模型)、传播(写回默认值)。我前两轮各只对准一件(且第一件还
猜错),所以两次"修好了"都复发。**遇到反复复发的故障,先把'触发/动作/
传播'拆成三栏,再看你的修法落在哪一栏**;只治传播 = 止血不治因,只治
触发 = 治因不止血。
