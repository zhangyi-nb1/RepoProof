# 踩坑与修复日志(复盘/面试素材,持续追加)

> 记录规则:每条 = 现象 → 根因 → 修复 → 教训。全部来自真实用户实测。

## 2026-08-08 · Guided 真实运行首日(用户亲测)

1. **URL 尾随空格导致找不到本地分析副本**
   现象:装配报"未找到 thefuzz 的分析副本"(实际存在)。根因:输入
   URL 带尾随空格,repo 名解析成 `thefuzz `。修复:URL 全清洗
   (strip / 去尾 `/` 与 `.git`)。教训:一切用户输入先归一化。
2. **wheelhouse 鸡生蛋:freeze --full 要求 wheelhouse,但 wheelhouse
   由 baseline 构建,baseline 又要求先 freeze**
   现象:冻结报 `expected exactly one thefuzz wheel, found []`。
   根因:benchmark 时代"freeze→baseline→freeze --full"三步隐含顺序
   从未被写成产品流程。修复:装配按钮改为显式三步序列。教训:
   专家肌肉记忆里的隐含顺序,必须在产品化时显式化。
3. **僵尸进程被判"仍在运行",UI 永远转圈**
   现象:任务 2 分 22 秒完成,UI 显示"正在运行"近 18 分钟。根因:
   后台进程结束成 defunct,`os.kill(pid,0)` 对僵尸返回成功。修复:
   完成判定改产物优先(run 目录出现 report.json 即完成),进程探测
   用 `ps stat` 且 Z 态判死。教训:判断"完成"永远看产物,不看进程。
4. **完成结果依赖运行锁,锁一清结果就"消失"**
   现象:切技术模式刷新后,完成横幅与结果无处可寻;回顾下拉只有
   3 个内置示例。根因:完成态渲染只依赖 .ui_live.lock,且下拉硬编码
   demo 案例,本地 runs/ 从未纳入。修复:运行进度页下拉纳入全部
   本地真实运行(「你的运行:…」,最新在前),从 report.json 持久
   渲染(verdict/AI状态/失败原因/技术详情),不再依赖锁。教训:
   UI 状态的唯一事实源是磁盘产物,锁只用于并发控制。
5. **同一任务两次运行结果分歧(PASS_ADAPTED → FAIL)**
   现象:第一次 04:48 PASS(16 调用内提交,141.6s);第二次 05:29
   FAIL——`TokenBudgetExhausted`:输入 468,081 tokens 超 400k 合同
   上限,11 次调用耗尽,验收未运行。定性:不是 bug——温度 0 下轨迹
   仍会因环境时序分叉,预算护栏正确触发。教训:这正是"独立验证 +
   预算合同"存在的意义;产品叙事上是最有说服力的一课(AI 自述不可
   靠,且资源无界消耗必须被合同拦住)。
6. **模型完成检测误报之前的连锁**(前日)
   Streamlit 旧进程模块缓存(import 的 state.py 不热重载)导致截图
   与断言陈旧——修复:改代码后必须全杀进程重启,不能信热重载。

7. **页面数据源割裂:三页三个数据源,用户运行"到处都找不到"**
   现象:历史记录只有 12 条公开基准,结果报告只有 3 个内置案例,
   用户亲手跑的 run 只在运行进度页短暂可见。根因:每页各自为政
   (benchmark_summary / demo CASES / 运行锁),没有统一的"运行目录"
   概念。修复:统一双源模型——公开基准(随项目发布,不可变)+
   你的运行(runs/*/report.json,持久)——历史记录分双区展示,
   结果报告与运行进度下拉均纳入本地运行并完整渲染(结论/原因/
   适配代码/打包下载/技术字段)。教训:先定义统一数据模型,再做
   页面;页面直接读各自数据源必然割裂。

8. **Docker(colima)停机 → 系统给 BLOCKED(external)而非 FAIL,零模型消耗**

16. **h1 探子的"静态可导入"前提 = 又一处验证便利性泄漏(#15 同族)+ 挂死调用吞掉 wall 执法**
    现象一:oracle h1 在自己进程静态 import 上游模块打桩;实现若在
    运行时才注入 sys.path(动态 import,合法且真实调用了钉版图),
    探子自身 ModuleNotFoundError → "真实调用"从未被测量却计为失分
    (v2 批 3 发中招,取证于 sample3 现场)。修法(task-v3):热身
    作业让模块进入 sys.modules 后,对**实际被用的模块对象**打桩。
    教训:provenance 探子必须挂在被测系统真实使用的对象上,而不是
    探子自己方便拿到的对象上。现象二:provider 降速时段一个不返回的
    API 调用让 runner 冻结 20+ 分钟,wall 预算在调用间隙才有检查点
    → 无单调用超时 = wall 执法可被单点挂死架空(order 13 人工中止,
    INFRA_ABORTED 不计模型账)。修法:agent 后端加单调用超时。

18. **复制带 venv 的目录再跑其工具 = 写穿原目录(shebang 绝对路径暗通道,F 类风险活案例)**
    现象:T3v2 工程搭台架,CoW 复制 bench 副本(内含 v1 工程遗留的
    `.venv`)到 /tmp 后直呼 `.venv/bin/pip install …`——pip 脚本
    shebang 是**绝对路径**,指回 bench 副本原位置 → 三条安装命令全部
    打进原副本的 venv;/tmp 侧 python(经 pyvenv.cfg 就地解析)则
    看到空环境,`import browser_use` 失败才暴露。取证:副本 git 树净
    (.venv 在 gitignore)、快照排除表含 .venv → 冻结材料与会话链路
    零污染;损害仅限工程遗留 venv 可能的传递依赖漂移(非承重件)。
    教训:**venv 不可复制不止是"复制后不可用",更是"复制后仍可用但
    用的是原环境"——脚本 shebang 是指回原目录的写通道**,与 TESTPLAN
    F 类"绝对路径配置"同族;修法:①复制目录前先剔除/复制后立即重建
    venv;②一律 `<新路径>/bin/python -m pip`,绝不直呼复制来的脚本;
    ③工程台架用完即清,不把 merged venv 留在 bench 副本里(本次的
    根因遗留)。harness 侧早已按"per-run venv 重建"设防,这次中招的
    是工程操作面——纪律对人(AI 操作员)同样生效。

19. **日志取证要打结构,不要打字符串——三轮误判同一个故障的方法论根因**
    现象:"Fable 降级"连续三轮定性,前两轮全错(①配额耗尽 ②用户级
    settings 默认值),第三轮才锁死真因(安全分类器旗标 → 静默换模 →
    降级态写回配置的棘轮,见 CASEBOOK 案例 2)。**三轮的差别不在思考
    深度,在证据类型**:前两轮是"读一个配置文件 + 推理",第三轮是
    "对 transcript 的结构化字段做统计"。对照实验就在同一次排查里——
    `grep -c fallback *.jsonl` 得 306 次命中,**全是噪声**(我自己写
    进对话的中文文档正文里的"fallback/降级/capacity");换成
    `jq 'select(.type=="system") | select(.content|contains("safeguards"))'`
    一次命中 **19 条真事件**,附时间戳、目标模型、措辞变体。教训:
    **正文 grep 在"日志里混有讨论该日志的文本"时必然自污染**(本项目
    尤甚:我们整天在对话里讨论降级),而 `type`/`stop_reason`/内容块
    `type:"fallback"` 这些**结构位是被测系统写的,不是被讨论出来的**。
    留档三条可复用取证式(RepoProof transcript 通用):
    ①模型切换点+上下文规模 `select(.type=="assistant")|[.timestamp,
    .message.model,(usage 三项求和)]`;②旗标事件 `select(.type==
    "system")|contains("safeguards")`;③停止原因分布 `.message.
    stop_reason` 按模型 group(本次由此发现 2 条 `refusal`=旗标的
    硬失败变体)。连带纪律:**用"我方是否写过这个词"来判断一个 grep
    命中是否可信**——这与 oracle 自持(LESSONS #15/16)同构:探子必须
    挂在被测系统实际写出的结构上,不能挂在双方共享的字符串上。

20. **进程身份判别只看可执行体段——命令行参数是"别人说的话",不是身份**
    现象(order-34 一手实证):postflight 清扫的 `BROWSER_PATTERN` 对
    **全命令行**大小写不敏感匹配 `chrome|chromium`,把 4 个用户 Claude
    Code 会话进程计入浏览器族——它们的**参数**里带
    `--allowedTools mcp__claude-in-chrome__…` 工具名。杀伤决策被第二道
    标记门保住(killed=0,零误杀=防御纵深生效),但 skipped_new/
    leftover_new_pids 作为测量报告失真。修复:判别面收窄到
    `executable_portion`(命令行到第一个 ` -` 参数边界;macOS 浏览器
    路径含空格故不能按空格切;截短方向=宁漏报不误报,与"绝不触碰用户
    进程"同向)。**这是 #19 的进程版**:参数串是进程"讨论到"的字符串
    (工具名、URL、日志路径都可能含 chrome 字样),可执行体段才是
    系统赋予的结构位。潜伏项:oracle 侧 h6/h7 的
    `pgrep -f "Chrome|chromium"` 同样是全命令行匹配,本次靠大小写敏感
    +差集窗口幸免,v3 统一收窄。连带测试工程陷阱(白拿会咬人):
    **macOS framework 构建的 python 启动即 re-exec 并把 argv[0] 改写为
    `Python.app/…/MacOS/Python`**——用"符号链接改名 python"造假进程名
    在 ps 里根本不出现;可靠做法是 sh 包装脚本(ps 显示
    `/bin/sh <脚本路径> <参数>`,nonce 落在可执行体段,与真实浏览器

21. **"未见阈值"是弱结论,"无因果"是强断言——中间隔着一张暴露率表**
    (2026-08-11,#19 的续集,用户反问逼出的第四轮取证)。#19 我用 jq 打
    结构位,查到 19 次旗标的上下文横跨 392k–938k **无阈值**,且 Fable 自身
    在 938,435 tokens 正常出活 → 我据此写下"与上下文窗口全无关"。**这一步
    外推是错的**。用户反问:"那我改成 150K 窗口后确实不降级了,怎么解释?"
    补做**危险率(每千轮命中数)**而非绝对计数:≤300k 累计 **1250 轮 0 命中**
    (均匀基线 5.6/千轮下期望 7 次,泊松 p≈0.0009),300–400k 1.6、
    400–500k 3.7、600–700k 12.7、700–800k 56.8、800–900k 125、900k+ 333。
    体量相关性极强。**"无阈值"和"强相关"并不矛盾**——真实机制是**危险率
    累积**:分类器打分对象是整个请求,而请求 = 全量 transcript,每段可疑
    内容被**逐轮重评**,单轮命中 ≈ 1−Π(1−pᵢ)。
    三条可复用教训:
    (a) **绝对计数会骗人,要除以暴露量**。19 次命中集中在高位桶,但高位桶
    轮次也少——不做归一化就看不出 700k+ 的危险率是 300k 段的 35 倍;
    (b) **零观测要配期望值才有说服力**。"1250 轮 0 命中"本身可能只是没跑够,
    算出泊松 p≈0.0009 才构成拒绝;
    (c) **多变量同时改 ⇒ 观察被混淆,不能当证据**。四键一起上,
    `switchModelsOnFlag:false` 单独就足以消除现象;窗口的独立贡献只能由
    危险率表证明,不能由"改完没再降级"证明。**这与本项目 prereg 纪律同构:
    一次只动一个自变量,否则事后无法归因。**
    同轮顺带纠错另一个方向性错误(用户与我都想反了):**压缩不费额度,省额度**。
    95–98.7% 输入是 `cache_read`(0.1x),按等效计费每轮成本对常驻上下文
    **超线性**(0–100k=18.3k → 900k+=1145.4k/轮,顶端缓存崩溃全量 1.25x 重写);
    逐会话对照:压缩 0 次的会话 77.2k/轮(最贵),压缩 6 次的 33.7k/轮(第二便宜)。
    **按原始 token 直觉估成本 = 忽略缓存分层,量级级错误**;压缩的真实代价是
    信息损失,不是钱。

## #27 · 给便利入口加纪律,必须同时加**机器可读的归属标**

**场景**:把 UI 从 T1 泛化到 T1–T4、允许用户随时加发观察方差。页面上写了
红框警告"这属于预注册之外的探索性发次,不能进正式结论",并用勾选框挡住
发射按钮——看起来纪律已经落实了。

**漏洞**:警告只写给人看。发次进 `runs.jsonl` 后,与预注册批次**字段完全
一样**;而 `count_passes()` 是闸门取数唯一入口,它照样会把探索性 PASS 数
进阶段通过数。台账 append-only,污染进去就只能再挂一层裁定去补救。

**这是 #26 的同一个病**:真话(这发不算数)写在了机器读不到的地方。区别
只在 #26 是事后发现,这次是**交付前自查发现**——功能是我加的,隐患也是我
带进来的。

**修法**:`batch` 字段随写入落盘(UI 发射路径强制打
`EXPLORATORY_UNPREREGISTERED`,CLI 给 `--batch`);`count_passes()` 两道
扣除(人工作废 + 探索性),`total` 仍含全部(如实入账不挑选);历史行无
该字段 → 视为预注册批次,不因新字段被追溯误扣。

**可迁移的判据**:每加一条"这个不算数"的规则,先问一句——**机器凭哪个
字段知道它不算数?** 答不上来,这条规则就只是一句注释。

## #28 · `ruff --fix` 不要对整个 src 跑

**踩坑**:为省事跑了 `ruff check --fix src/repoproof tests`,它顺手改了两个
与本次改动无关的文件:`feature_stack.py`(T4 事务栈机器,22 项钉死锁着
行为)与 `test_postflight.py`,做了 `timezone.utc→UTC`、去前向引用引号等
美化。改动本身安全,但它们混进了一个"讲批次归属"的提交里。

**为什么要在意**:(a) 冻结/钉死组件的无关改动会稀释 provenance——日后回看
提交,分不清哪些行是为修 bug 动的、哪些是格式化蹭的;(b) 自护栏项目里,
无关文件的静默改动正是回归假警报的来源(见 #26 的并发编辑教训)。

**纪律**:`--fix` 只对**本次实际编辑过的文件**跑;全仓库 lint 用只读的
`ruff check`(不带 `--fix`),存量问题单独立项修,不搭便车。
