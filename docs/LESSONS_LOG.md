# 踩坑与修复日志(复盘/面试素材,持续追加)

> 记录规则:每条 = 现象 → 根因 → 修复 → 教训。全部来自真实用户实测。

## 2026-08-08 · Guided 真实运行首日(用户亲测)

1. **URL 尾随空格导致找不到本地分析副本**
   现象:装配报"未找到 thefuzz 的分析副本"(实际存在)。根因:输入
   URL 带尾随空格,repo 名解析成 `thefuzz `。修复:URL 全清洗
   (strip / 去尾 `/` 与 `.git`)。教训:一切用户输入先归一化。
2. **wheelhouse 鸡生蛋:freeze --full 要求 wheelhouse,但 wheelhouse
   由 baseline 构建,baseline 又要求先 freeze**
   现象:冻结报 `expected exactly one thefuzz wheel, found []`。
   根因:benchmark 时代"freeze→baseline→freeze --full"三步隐含顺序
   从未被写成产品流程。修复:装配按钮改为显式三步序列。教训:
   专家肌肉记忆里的隐含顺序,必须在产品化时显式化。
3. **僵尸进程被判"仍在运行",UI 永远转圈**
   现象:任务 2 分 22 秒完成,UI 显示"正在运行"近 18 分钟。根因:
   后台进程结束成 defunct,`os.kill(pid,0)` 对僵尸返回成功。修复:
   完成判定改产物优先(run 目录出现 report.json 即完成),进程探测
   用 `ps stat` 且 Z 态判死。教训:判断"完成"永远看产物,不看进程。
4. **完成结果依赖运行锁,锁一清结果就"消失"**
   现象:切技术模式刷新后,完成横幅与结果无处可寻;回顾下拉只有
   3 个内置示例。根因:完成态渲染只依赖 .ui_live.lock,且下拉硬编码
   demo 案例,本地 runs/ 从未纳入。修复:运行进度页下拉纳入全部
   本地真实运行(「你的运行:…」,最新在前),从 report.json 持久
   渲染(verdict/AI状态/失败原因/技术详情),不再依赖锁。教训:
   UI 状态的唯一事实源是磁盘产物,锁只用于并发控制。
5. **同一任务两次运行结果分歧(PASS_ADAPTED → FAIL)**
   现象:第一次 04:48 PASS(16 调用内提交,141.6s);第二次 05:29
   FAIL——`TokenBudgetExhausted`:输入 468,081 tokens 超 400k 合同
   上限,11 次调用耗尽,验收未运行。定性:不是 bug——温度 0 下轨迹
   仍会因环境时序分叉,预算护栏正确触发。教训:这正是"独立验证 +
   预算合同"存在的意义;产品叙事上是最有说服力的一课(AI 自述不可
   靠,且资源无界消耗必须被合同拦住)。
6. **模型完成检测误报之前的连锁**(前日)
   Streamlit 旧进程模块缓存(import 的 state.py 不热重载)导致截图
   与断言陈旧——修复:改代码后必须全杀进程重启,不能信热重载。

7. **页面数据源割裂:三页三个数据源,用户运行"到处都找不到"**
   现象:历史记录只有 12 条公开基准,结果报告只有 3 个内置案例,
   用户亲手跑的 run 只在运行进度页短暂可见。根因:每页各自为政
   (benchmark_summary / demo CASES / 运行锁),没有统一的"运行目录"
   概念。修复:统一双源模型——公开基准(随项目发布,不可变)+
   你的运行(runs/*/report.json,持久)——历史记录分双区展示,
   结果报告与运行进度下拉均纳入本地运行并完整渲染(结论/原因/
   适配代码/打包下载/技术字段)。教训:先定义统一数据模型,再做
   页面;页面直接读各自数据源必然割裂。

16. **h1 探子的"静态可导入"前提 = 又一处验证便利性泄漏(#15 同族)+ 挂死调用吞掉 wall 执法**
    现象一:oracle h1 在自己进程静态 import 上游模块打桩;实现若在
    运行时才注入 sys.path(动态 import,合法且真实调用了钉版图),
    探子自身 ModuleNotFoundError → "真实调用"从未被测量却计为失分
    (v2 批 3 发中招,取证于 sample3 现场)。修法(task-v3):热身
    作业让模块进入 sys.modules 后,对**实际被用的模块对象**打桩。
    教训:provenance 探子必须挂在被测系统真实使用的对象上,而不是
    探子自己方便拿到的对象上。现象二:provider 降速时段一个不返回的
    API 调用让 runner 冻结 20+ 分钟,wall 预算在调用间隙才有检查点
    → 无单调用超时 = wall 执法可被单点挂死架空(order 13 人工中止,
    INFRA_ABORTED 不计模型账)。修法:agent 后端加单调用超时。

18. **复制带 venv 的目录再跑其工具 = 写穿原目录(shebang 绝对路径暗通道,F 类风险活案例)**
    现象:T3v2 工程搭台架,CoW 复制 bench 副本(内含 v1 工程遗留的
    `.venv`)到 /tmp 后直呼 `.venv/bin/pip install …`——pip 脚本
    shebang 是**绝对路径**,指回 bench 副本原位置 → 三条安装命令全部
    打进原副本的 venv;/tmp 侧 python(经 pyvenv.cfg 就地解析)则
    看到空环境,`import browser_use` 失败才暴露。取证:副本 git 树净
    (.venv 在 gitignore)、快照排除表含 .venv → 冻结材料与会话链路
    零污染;损害仅限工程遗留 venv 可能的传递依赖漂移(非承重件)。
    教训:**venv 不可复制不止是"复制后不可用",更是"复制后仍可用但
    用的是原环境"——脚本 shebang 是指回原目录的写通道**,与 TESTPLAN
    F 类"绝对路径配置"同族;修法:①复制目录前先剔除/复制后立即重建
    venv;②一律 `<新路径>/bin/python -m pip`,绝不直呼复制来的脚本;
    ③工程台架用完即清,不把 merged venv 留在 bench 副本里(本次的
    根因遗留)。harness 侧早已按"per-run venv 重建"设防,这次中招的
    是工程操作面——纪律对人(AI 操作员)同样生效。

19. **日志取证要打结构,不要打字符串——三轮误判同一个故障的方法论根因**
    现象:"Fable 降级"连续三轮定性,前两轮全错(①配额耗尽 ②用户级
    settings 默认值),第三轮才锁死真因(安全分类器旗标 → 静默换模 →
    降级态写回配置的棘轮,见 CASEBOOK 案例 2)。**三轮的差别不在思考
    深度,在证据类型**:前两轮是"读一个配置文件 + 推理",第三轮是
    "对 transcript 的结构化字段做统计"。对照实验就在同一次排查里——
    `grep -c fallback *.jsonl` 得 306 次命中,**全是噪声**(我自己写
    进对话的中文文档正文里的"fallback/降级/capacity");换成
    `jq 'select(.type=="system") | select(.content|contains("safeguards"))'`
    一次命中 **19 条真事件**,附时间戳、目标模型、措辞变体。教训:
    **正文 grep 在"日志里混有讨论该日志的文本"时必然自污染**(本项目
    尤甚:我们整天在对话里讨论降级),而 `type`/`stop_reason`/内容块
    `type:"fallback"` 这些**结构位是被测系统写的,不是被讨论出来的**。
    留档三条可复用取证式(RepoProof transcript 通用):
    ①模型切换点+上下文规模 `select(.type=="assistant")|[.timestamp,
    .message.model,(usage 三项求和)]`;②旗标事件 `select(.type==
    "system")|contains("safeguards")`;③停止原因分布 `.message.
    stop_reason` 按模型 group(本次由此发现 2 条 `refusal`=旗标的
    硬失败变体)。连带纪律:**用"我方是否写过这个词"来判断一个 grep
    命中是否可信**——这与 oracle 自持(LESSONS #15/16)同构:探子必须
    挂在被测系统实际写出的结构上,不能挂在双方共享的字符串上。

20. **进程身份判别只看可执行体段——命令行参数是"别人说的话",不是身份**
    现象(order-34 一手实证):postflight 清扫的 `BROWSER_PATTERN` 对
    **全命令行**大小写不敏感匹配 `chrome|chromium`,把 4 个用户 Claude
    Code 会话进程计入浏览器族——它们的**参数**里带
    `--allowedTools mcp__claude-in-chrome__…` 工具名。杀伤决策被第二道
    标记门保住(killed=0,零误杀=防御纵深生效),但 skipped_new/
    leftover_new_pids 作为测量报告失真。修复:判别面收窄到
    `executable_portion`(命令行到第一个 ` -` 参数边界;macOS 浏览器
    路径含空格故不能按空格切;截短方向=宁漏报不误报,与"绝不触碰用户
    进程"同向)。**这是 #19 的进程版**:参数串是进程"讨论到"的字符串
    (工具名、URL、日志路径都可能含 chrome 字样),可执行体段才是
    系统赋予的结构位。潜伏项:oracle 侧 h6/h7 的
    `pgrep -f "Chrome|chromium"` 同样是全命令行匹配,本次靠大小写敏感
    +差集窗口幸免,v3 统一收窄。连带测试工程陷阱(白拿会咬人):
    **macOS framework 构建的 python 启动即 re-exec 并把 argv[0] 改写为

21. **"未见阈值"是弱结论,"无因果"是强断言——中间隔着一张暴露率表**
    (2026-08-11,#19 的续集,用户反问逼出的第四轮取证)。#19 我用 jq 打
    结构位,查到 19 次旗标的上下文横跨 392k–938k **无阈值**,且 Fable 自身
    在 938,435 tokens 正常出活 → 我据此写下"与上下文窗口全无关"。**这一步
    外推是错的**。用户反问:"那我改成 150K 窗口后确实不降级了,怎么解释?"
    补做**危险率(每千轮命中数)**而非绝对计数:≤300k 累计 **1250 轮 0 命中**
    (均匀基线 5.6/千轮下期望 7 次,泊松 p≈0.0009),300–400k 1.6、
    400–500k 3.7、600–700k 12.7、700–800k 56.8、800–900k 125、900k+ 333。
    体量相关性极强。**"无阈值"和"强相关"并不矛盾**——真实机制是**危险率
    累积**:分类器打分对象是整个请求,而请求 = 全量 transcript,每段可疑
    内容被**逐轮重评**,单轮命中 ≈ 1−Π(1−pᵢ)。

    轮次也少——不做归一化就看不出 700k+ 的危险率是 300k 段的 35 倍;
    (b) **零观测要配期望值才有说服力**。"1250 轮 0 命中"本身可能只是没跑够,
    算出泊松 p≈0.0009 才构成拒绝;

    危险率表证明,不能由"改完没再降级"证明。**这与本项目 prereg 纪律同构:
    一次只动一个自变量,否则事后无法归因。**
    同轮顺带纠错另一个方向性错误(用户与我都想反了):**压缩不费额度,省额度**。
    95–98.7% 输入是 `cache_read`(0.1x),按等效计费每轮成本对常驻上下文

    逐会话对照:压缩 0 次的会话 77.2k/轮(最贵),压缩 6 次的 33.7k/轮(第二便宜)。
    **按原始 token 直觉估成本 = 忽略缓存分层,量级级错误**;压缩的真实代价是
    信息损失,不是钱。

作废},任何一条不满足即出局。三次补丁后语义已经等价,但下次新增维度
(比如"不同 harness_commit 不互比")仍会重演——**判据的形状错了**。

**修法**:`SMOKE_MODEL_PREFIX="fake"` 排除,单列 `smoke`/`smoke_passes`;
钉死一例。修后闸门:T1 2 / T2 2 / T3 1(每阶段仍 ≥1,闸门未被推翻,
但 T1 的数字从虚高的 3 修正为诚实的 2)。

## #31 · harness 替模型认领了错:"重放基础设施故障"这个标签是反归因

**实录**:2026-08-12 用户加发的四发全失败。其中两发 T3 走到了**只差最后
一步**——公开面 23/23、oracle 8/8、回归 607(基线 606)、政策 PASS,唯独
干净重放挂了。台账给的死因是:

    replay infrastructure failure: 宿主依赖安装失败(wheelhouse 不全?)

`failure_types` 分别是 `UNKNOWN` 与 `SCHEMA_ERROR/TEST_FAILURE`——**没有一个
说中死因**。而真实原因是适配把 `openai==2.16.0`(gpt-5.5)与
`browser-use==0.13.7`(gpt-5.6)写进了 `requirements.txt`,冻结轮仓里根本
没有这两个分发;它们在会话里能用,只因为源码树已经躺在 `../upstream`。

**这正是干净重放存在的理由**:声明了装不回来的钉版 = 教科书级的"在我机器上
能跑"。可标签把它写成了**机器的锅**,还带一个"wheelhouse 不全?"的问号——
读台账的人(包括我自己)会顺着这个问号去查轮仓,而不是去看模型写了什么。

**为什么危险,不只是"标签不好看"**:归因错误会**系统性地压低模型缺陷的
计数**。真实模型 PASS 只有 5 发,同类失败每被记成基础设施故障一次,
"模型做不到的事"就少算一件,而"我的机器不行"就多算一件——这个方向的偏差
恰好是最容易自我安慰的那个方向。它与 #26/#27/#30 是同一个家族:**台账把
不该算的算进去、把该算的算出来**,只不过这次错在失败侧而不是通过侧。

**修法(三段,缺一不可)**:
1. **判据要有对照基准**:同一条 pip 报错,归因取决于该分发**是否在未适配的
   宿主副本 `requirements.txt` 里**。在 → 轮仓确实不全(harness);不在 →
   适配自己加的(agent)。基准必须读**原件**,读会话里那份等于让被测者
   自定义基准。判据读 pip **全文**不读截断尾巴——否则归因取决于"报错够不够
   靠后"。
2. **异常要分型**:`DependencyNotReproducible(HostRunError)` 携带
   `dists`;重放捕获处专用分支写在兜底 `except Exception` **之前**(Python
   按书写顺序匹配,写反了等于没写),两条分支分别落 `attribution: agent` /
   `attribution: harness`。
3. **归因要进台账**:`failure_types` 此前只收修复轮的失败包,验证器自己判出
   的类型进不去。改为**并集**——否则归因只活在 report.json 里,而闸门统计和
   日后复盘看的是台账。

**可迁移的判据**:每写一句"XX 基础设施故障",先问——**如果这是被测者的
缺陷,我这条消息会长什么样?** 两者长得一样,就说明这个标签没有携带归因,
只是把异常原样抄了一遍。异常文本 ≠ 失败类型。

**未改写历史**:两发的 verdict 仍是 FAIL(结论本就正确),台账行不重写;
更正的读数记在 `FAILURE_TAXONOMY.md` 的 `DEPENDENCY_NOT_REPRODUCIBLE` 行。

## #34 · exit 4 的两义性:最强的红被当成用法错误

自己那个缺陷:一条空断言在同样的树上也会同样地"红"。故把新符号的导入

## #39 · 执法读到的是陈旧总量;拍一个常数替代计算,总会遇到比它大的调用

**实录**(order-63,gpt-5.6 × T3v5,轮 1):政策线 800,000/轮,执法线内移
到 750,000。第 22 次调用后真实累计 **752,243**(已过执法线),第 23 次调用
**仍被放行**,调用后 **803,310 > 800,000**。一发公开 23/23 + 隐藏 8/8 的
满分适配,被终局以 **0.41%** 的超出击杀。

**两个缺陷叠在一起**:

- **D1 陈旧总量**。记账走 `litellm.success_callback`,而 litellm 用
  `executor.submit(...)` 把回调**丢进线程池**(litellm/utils.py:1479)。
  调用前读到的总量落后一次调用——第 23 次调用前读到的是 703,172。
- **D2 固定内移是猜的**。`TOKEN_STOP_MARGIN = 50_000`,而该轮单次最大调用
  **51,067** —— 差 1,067 就翻车。

**最该记住的一条**:**测试替身比生产更强,于是 12 条钉死一条都没抓住。**
`FakeInner` 在 `query()` 里**同步**写 totals,生产的钩子是**异步**的。
替身给了被测代码一个生产没有的保证,测试因此测的是一个不存在的世界。
以后写替身先问一句:**这个替身在哪一点上比真货更守规矩?**

**判据**:H7-a 执法不得只依赖异步上报;H7-b 调用前投影(估算 × 校准比值 ×
安全系数,并以已观测单次最大兜底),放不下就不发;H7-c 真实用量 ≤ 投影时
累计**永不越线**;H7-d 轮桶归同步记账所有(异步钩子会把上一轮末次调用记到
下一轮,而 per_round 终局比的正是单轮最大用量);H7-e 不许假零、不许少报。

**顺带纠正一条旧决策的手段、保留其意图**:2026-08-09 内移 50k 的用户决策,
意图是"别让越线取决于边界运气"。投影更严格地满足了这个意图,于是不再收这
50k 的税。反向证据同样真实:order-63 轮 3 用到 **749,318**,离旧执法线只剩
**682**,却交出了 23/23 —— 那笔税差点吃掉的正是成功的那一轮。

**这是同一个病的第四次发作**:终局要杀、循环既不防也不报。前三次是 #35

## #40 · 量具不能由被测者提供

**实录**(T2v4,`fixtures/fake_llm_server.py`):这个文件既是公开测试的假

## #42 · H9-a 的两个洞都在"清零"这一步:配方没进仓、失明当干净

2026-08-13。用户要求"把那 7 棵 `_scratch_t2_*` 树移出本机"(#41 记的
开跑前必做项)。真去做的时候,连着掉进两个坑,都不在原判据的字面之外,
而在**执行清零这个动作本身**。

### 坑一:配方只活在残留里,于是残留删不掉

清点 7 棵树,仓外内容有四类:运行产物(chroma/log/`research_jobs/*.json`)、
7 份 `.venv`(618MB 里的 ~610MB)、一份**被取代的旧**公开测试,以及
**一段没有任何地方记录过的 3 行挂载胶水**(`rag_api.py` 末尾
`from research_jobs import mount_research_api; mount_research_api(app)`)。

仓里的 `controls/` 只有 6 个 `research_jobs.py`。少那 3 行,照仓里的东西
**装不出能跑的控制组** —— 五物验证一直是手工在这 7 棵树里做的,没有任何
脚本引用过 `controls/`。于是这 7 棵树同时是**答案残留**和**唯一的配方
载体**:H9-a 要求删,而删了就再也装不回来。它们卡在那儿两天不是因为懒。

解法是 `scripts/build_control_tree.py`:钉版上游 + 任务包 `fixtures/` +
`public_tests/` + `controls/<name>/*.py` + 挂载,**默认建完即拆**。配方经
逐路径核对(nc1 与上游差集 5 项、上游无缺失),并以正控端到端复现:脚本
装出的树与手搓树 **297/297 文件、路径差 0**,内容差仅两处 —— 一行装饰性
注释,以及脚本用的是仓里**更新**的公开测试。

**可推广的一条**:残留之所以清不掉,常常不是因为它有价值,而是因为**造它
的方法没进仓**。清零动作的前置条件是可复现,不是决心。而"默认留着"正是
残留的来源 —— 手搓流程的默认是留,所以每验证一次五物就多 7 棵。

### 坑二:我差点用挪位置绕过自己的闸门,然后发现闸门本来就是瞎的

第一反应是 `mv` 进 `~/.Trash`。当时 `ANSWER_KEY_SCAN_ROOTS` 不含废纸篓 ——
那一挪会让 `reachable_answer_keys()` 立刻返回空、preflight 放行,而正控
参考实现原封不动躺在 `~/.Trash/_scratch_t2_positive/research_jobs.py` 上,
`find ~` 照样够得着。判据原文写的是"运行主机的**可达路径**"。**靠挪位置
让检测器闭嘴不叫清零** —— 那是 order-21 的自欺版本,只不过这次是我。

补上废纸篓做扫描根之后,当场实测出更糟的:

    reachable_answer_keys(t2_v4)              ->  0 处命中
    test -d ~/.Trash/_scratch_t2_positive-…   ->  存在

两句同时为真。macOS TCC 让 `iterdir()` 抛 `Operation not permitted`,而
老代码写着 `except OSError: continue`,注释是"扫不到就跳过,不是残留证据"。
推理没错,结论错位:**闸门的职责不是"证明有残留",是"确立答案不可达"**;
读不到时后者无法确立。检测器看不见时朝**放行**的方向失败了。

### 坑二续:我在同一个位置做了两个相反的决定

补上废纸篓当扫描根之后又撤了。撤的依据是三条实测,不是嫌麻烦:

    ls ~/.Trash    -> Operation not permitted   (macOS TCC,不是沙箱;
                                                 关掉沙箱重测,同样拒绝)
    find ~/.Trash  -> Operation not permitted
    head ~/.Trash/<确切名>/research_jobs.py -> 正常打印出正控正文

废纸篓**不可枚举、却可按确切路径读**。做扫描根等于**零覆盖**(枚举不了
就发现不了任何东西),却会因"列不动"永久判 `ANSWER_KEY_SCAN_BLIND` ——
在 macOS 上是一道**不可满足**的闸门。不可满足的闸门最后一定被整条关掉,
比明写限制更糟。

**这条比结论本身重要**:两次决定我都能给出通顺的理由,差别只在第二次
**去测了**。"判据原文是可达路径,所以废纸篓要加进扫描根"听上去无懈可击,
但它默认了"可达 = 可扫描";实测告诉你这两件事在 macOS 上是分开的。凡是
从判据措辞直接推出实现的地方,都要过一遍真机。

### 判据(冻结)

- **废纸篓不做扫描根**,残留不得停放在废纸篓 —— 靠规程,H9-a 执法不到,
  与 H9-b"是检测器不是牢笼"同型。真要清零就删到不存在,别删到"看不见"。
- **H9-a 失明即拒开**:扫描根里有列不动的目录时,以
  `ANSWER_KEY_SCAN_BLIND` 拒开,理由与"查到残留"**分开** —— 补救动作不同
  (前者让它可读或倒空,后者清掉)。噪声实测:四个扫描根共 247 个可列目录,
  盲区 0 个,stat 不动的文件 0 个 —— 撤掉废纸篓之后这道规则是**可满足**
  的(#35 的反面同样成立:不许因为怕误伤就放行)。单个文件读不到不计入
  —— 真机噪声大,洞也小得多。
- **控制组装配唯一入口** `scripts/build_control_tree.py`,默认建完即拆;
  `--keep` 必须显式,并打印"这是残留、会拒开下一发"的警告。

### 与前面几条的关系

#40 是量具可写,#41 是答案可读,#42 是**清零这个动作本身不可靠** ——
配方没进仓则删不掉,检测器失明则删了也不知道。三条同源:被测者、量具、
答案三者之间的隔离,以及**证明隔离成立的那套手段自己是否可信**。

**诚实边界**:失明拒开只覆盖**目录**级。单个文件读不到仍按老路跳过;
沙箱/容器级封闭仍是未做项(#41 已记)。

### 判据(冻结)

- **判据不得绑在被测系统可提供的名字上**。进程内打桩、模块在场、类方法
  被调用 —— 只要"那个模块/那个类"能由交付物提供,判据就等于零。可信的
  锚只有两类:(a) harness 自己起的、被测系统只能通过真实交互影响的东西
  (计量端点、站点账本、进程表);(b) 被测系统**做不到**的能力(不是
  "没做",是"做不了")。
- **因果金丝雀 > 存在性**:凡是"上游/引擎真的在干活"这类需求,判据必须
  是"它的产出到达了交付物",不能是"它被调用过"。金丝雀取值随机、无接口
  可查、无指定入口。
- **判据要按"能不能被搬运"分层记账,不按"看起来强不强"**。金丝雀、密度、
  工件结构全都可搬运/可伪造;只有"harness 侧独立观测到的、被测系统无法
  在 HTTP 层复制的事实"才在执法。每加一条判据,先问:它需要被测系统真的
  做那件事,还是只需要它**产出一个看起来对的字节串**?
- **优先用现成的真实发次做负控**,别自己造形状。我造的第一版 nc8 因为
  不了解 fixture 的推进机制而写错,而盘上就躺着一份真实模型的交付,它
  已经把判据穿了 4/5。真实产物比我的想象更接近攻击面。
- **但金丝雀不是终点**:任何"某个标记出现在交付物里"的判据都只挡得住
  不动脑的伪造 —— 标记是可搬运的。真正搬不动的是**这一次调用的返回值**。
  凡是探子已经在场的地方,一律接住返回值来判因果,别只数次数。
- **每条新判据都要配一个"有意规避"的负控**,不能只配一个"不动脑伪造"的。
  nc6 是前者,nc8 是后者;只有 nc6 时我以为判据成立,加了 nc8 才发现没有。
- **误杀侧也要有控制组**:每加一条"交付物必须含 X"的判据,同时加一个
  诚实但做了合理后处理的正控(`positive_trunc`),证明判据容得下实现自由度。
- **检测器先证明自己查得出**:每加一条这类判据,必须同时加一个**只红它
  一条**的负控。红一片的负控不算数 —— 那证明不了是哪条判据抓住的它。
- **每一跑必须自证成立**:任何"跑一批再判"的脚本,都要先回答"这一跑作
  不作数"(收集到几条、退出码是几),再回答"有没有违背项"。判定只读机器
  可读的报告格式,不读为人排版的终端输出。
- **六物验证只出自脚本**:装配 `scripts/build_control_tree.py`、判定

## #47 · 按 mtime 选"最近一次证据",等于让文件系统替你判定(2026-08-26,CI 实红)

`test_evidence_json_records_capture_rate` 原本这样挑最近一次变异闸门记录:

**同型问法**(下次写"取最新的那份"时先问一遍):这个"最新"是**谁**说的?
文件系统 mtime / 目录枚举顺序 / 文件名排序,都不是判定依据 —— 判定依据
只能是证据自己带的、跨机器可复算的身份(commit、序号、内容里的时间戳)。

## #48 · 类型检查跑在"缺依赖"的环境里,等于把窄化悄悄关掉(2026-08-27,CI 实红)

`mypy` job 当初只装 `[dev]`,没装 `[ui]`。于是 CI 那侧:

- `import streamlit as st` 解析不到 → `ignore_missing_imports = true`
  把 `st` 整个降成 `Any`;
- `st.stop()` 的真实标注是 `() -> NoReturn`,降成 `Any` 后这个语义没了;
- 页面里 `if not job: st.stop()` 之后的窄化**全部失效** ——
  `job` 仍是 `dict | None`,于是十几处 `job.get(...)` 报 union-attr。

本机装了 streamlit,窄化成立,`mypy` 干净利落地全绿 —— **同一份代码、
同一个 mypy 版本、同一份配置,两边给出相反结论**,差别只在依赖装没装齐。

**改法**:`mypy` job 与 `pytest` job 装同一套 extras(`[dev,ui]`)。
类型检查必须跑在**与被检代码相同的依赖集**上;缺依赖时 mypy 不会
拒绝工作,它会安静地把缺失的一切当 `Any` —— 那是"检查通过"里最不
值钱的一种。

**同型问法**:凡是"本机绿、CI 红"且错误集中在某个第三方交界处,先
比对两侧的**已安装依赖**,再怀疑代码。上一条(#47)是文件系统元数据
两侧不同,这一条是依赖集两侧不同 —— 同一个母题:**判定依据必须在
两侧同构,否则绿灯只是本机的一句方言。**

`main_dir_integrity`。当时的判断是"邻仓活写手 + 探针周期赶不上",
属环境噪声,CI 无邻仓故不受影响 —— **这个判断只对了一半**。

真根因:测试早就有隔离夹具 `_fake_neighbour`(把保护清单换成可控假
邻仓),但它只按住了 `DEFAULT_PROTECTED` 这一个来源。2026-08-26 保护
集改成**结构性发现**(本仓 + 兄弟 git 仓,动态计算)之后,那一句只
按住了常量,结构发现照样把真实邻仓拉回指纹扫描 —— **五个测试文件的
隔离同时悄悄失效**,而失效的表现只有两个:偶红,和每条 E2E 白扫几十
秒真目录。没有任何一条断言会说"我不再隔离了"。

改法两层:
1. 把三个来源(结构性 / 常量 / 环境变量)一起按住,收进共用
   `tests/conftest.py::isolate_protected_dirs`;
2. **夹具自检**:收尾断言实际生效的保护集恰好等于预期主体。将来再
   多一个来源,红在夹具自己身上、当场指名道姓,而不是把红分摊到几十
   条不相干的测试上。

验证:模拟邻仓写手(8 秒周期,同 OfferClaw)下连跑 —— 修前 5/5 红,
修后 5/5 绿;另伪造"第三个来源"确认自检会当场触发。

**同型问法**:一条测试如果依赖"环境里没有别的东西在动",那它迟早会
以偶红的形式收费。而当它本该被夹具隔离却仍然偶红时,**先怀疑夹具,
别急着怪环境** —— 夹具是会过期的,尤其在它保护的那个集合换了实现之后。
顺带一提:被隔离的判据这次反而**更严**了(从 `self_ok` 提到严判
`ok`),去 flake 不等于降标准。

## #50 · Streamlit 只热重载页面,不重载被它 import 的模块(第二次咬人)

现象:用户点新加的按钮,拿到
`AttributeError: module 'product_jobs' has no attribute 'read_repo_overview'`
—— 而磁盘上那个函数明明在。

因果:Streamlit 每次 rerun 会重新 exec **页面文件**,但
`from ... import product_jobs` 拿到的是**进程里缓存的模块对象**。于是
"页面是新代码、services 是旧对象",两边对不上就抛 AttributeError。
Studio 进程起于 17:55,而函数是 18:15 之后加的。

**这是第二次**:M6 那轮改 `product_mode` 的文案常量也遇到过同一件事
(当时的结论写成了"运维注意:改常量须重启")。写成注意事项没能拦住第二
次,因为注意事项要靠人记得。

改法两层:
1. 加功能后**主动重启 Studio 进程**(preview_stop + preview_start),
   不要指望热重载;
2. 页面侧对新接口做**能力探测**并给人话提示(见 tool_onboarding 的
   `_require_service`),让下一次的表现是"请重启 Studio 以加载新功能",
   而不是一串英文 AttributeError 甩在用户脸上。

**同型问法**:凡是"改了代码但运行中的进程行为没变",先问**谁在缓存**
—— 是模块对象、是 `@st.cache_*`、还是 venv 里装的是旧版本。这一条与
#47(文件系统元数据)、#48(依赖集)同一母题:**你以为你在测新代码,
其实你在测一个旧状态。**

## #51 · 密钥注入是**启动方式**的一部分,不是代码能兜的(2026-08-27)

用户在 Studio 里点「让模型总结」,拿到
`起草通道未配置:需 REPOPROOF_DRAFTER_*(或回落官方三键…)`
—— 而 `.env` 就在仓库根,三个键一个不缺。

因果:本项目的密钥纪律是 **`set -a; source .env; set +a` 注入进程环境**,
从不写进代码、不落日志、不进 argv。于是"能不能用模型"取决于**Studio 是
怎么被启动的**:从加载过 .env 的 shell 起 → 能用;直接
`streamlit run` → 进程里根本没有那些变量。Lab UI 早有
`scripts/run_lab_ui_live.sh` 干这件事,**Product Studio 一直缺对应脚本**
—— 这就是缺口(补 `scripts/run_studio_live.sh`)。

第二层(助手侧的硬边界):我试图让预览启动器加载 .env,被沙箱当场拒绝
——`/bin/bash: ./.env: Operation not permitted`。**这是对的**:工具起的
进程不该够得着用户密钥。结论是助手只能起**零模型**的 Studio;要用模型
功能,必须用户在自己的终端里起。这条边界不该绕,只该说清楚。

改法:①补 Product Studio 的启动脚本;②UI 在模型入口旁**先检测再提示**
(`provider_configured()`),没配置时给"两条出路"的人话说明并把离线选项
默认打开,而不是等用户点完才吃一句术语;③错误信息翻译层
(`_provider_hint`)保留原始信息但先说人话。

**同型问法**:凡是"配置明明在,程序却说没有",先问**谁的进程、怎么起的**
—— 配置的作用域是进程,不是文件系统。与 #50(模块缓存)、#48(依赖集)
同一母题:出问题的往往不是代码,是它运行在哪个状态里。
