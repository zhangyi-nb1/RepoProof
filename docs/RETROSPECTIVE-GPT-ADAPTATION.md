## 2. 这条线在做什么(问题定义)

RepoProof 要回答的是:**给定一个真实开源仓 + 一个模型看不见的隐藏验收
(hidden oracle),模型能不能把这个仓改到验收通过。** 本线把这套东西对准
GPT 系模型做适配与测量,同时要解决一个更难的前置问题:

> **题从哪来?** 用模型训练数据里已有的任务,测的是记忆不是能力。
> 所以任务必须是 **post-cutoff**(合并时间晚于模型知识截止)且
> **不可从题面推导**。这个"出题"问题最终成了本线最大的成本项 —— 见 §3.7。

## 3. 阶段过程与结论(时间线)

### 3.1 T1 / T2 / T3 三级台阶(2026-08-09 ~ 08-13)

宿主 = OfferClaw(自有项目),难度递增的三个真实集成任务:

| 台阶 | 任务 | 结论 |
|---|---|---|
| **T1** fastapi-mcp | 集成 MCP 服务 | 首个完整 **PASS_ADAPTED**(gpt-5.5 第 2 发);三模型完赛 |
| **T2** ODR | 依赖冲突(家族撕裂型) | 六发零 PASS 的诚实台阶 → task-v4 达成**首个端到端 PASS(双模型)** |
| **T3** browser-use | 浏览器自动化 | v1–v6 六代;v6 换**结构型锚**(harness-owned sidecar) |

诊断出"**repair 盲区**"(模型改对了但修复轮拿不到有效反馈信号),
开出处方后 task-v4 直接双模型 PASS。这是本线第一次证明
**失败可以归因到 harness 而不是模型**。

**T2/T3 稳定性差距(未完全关闭)**:稳定判据 S1–S3 立起来了,前三层
(执法漏洞 / 隔离 / T2v5 金丝雀)已修并验证,**剩模型侧未验** —— 这正是

### 3.2 模型降级事故与治理(2026-08-11)

**事故**:测试中途模型被静默降级,数字失真。
**三次归因迭代**(全部留痕,方法论价值大于事故本身):
1. 初判"配额用尽" → 错;
2. 再判"配置默认值" → 部分对;
3. 最终用 **transcript 结构化取证**锁死真因:**安全旗标触发 → 静默换模 →

**治理**:四键配置 + 冷启动钩子 + 30 秒取证式复验。
**教训入档**:凡"模型表现突变",先取证再归因;猜因会训练出错误的处方。

## 4. 核心结论(重走此线时最该先知道的)

### 4.1 关于 GPT 在本 harness 下的表现

- **v2 构造法下,gpt-5.5 / gpt-5.6 在 click-3581 与 sqlglot-8042 上都能过**
  (各自单发实测,cache 命中 89–90%);
- **同一模型 v1 FAIL → v2 PASS**(sqlglot-8042 × gpt-5.5)——
  **失败首先归因于出题与 harness,而不是模型能力**;
- **成本画像**(单发实测):
  8042×5.5 = 696K in / 16 分;8042×5.6 = 428K in / 20 分;
  3581×5.5 = 177K in / 3 分;3581×5.6 = 222K in / 6 分;
- **"过了一次"尚未坐实成"稳定过"** —— n=3 复测(P3)**未执行**。

### 4.2 关于测量方法(比模型结论更耐用)

1. **循环 vs 闸门对齐律**:闸门要杀的必须先教;闸门不杀的不许暗中判死。
   两次事故实录在 `LESSONS_LOG`。
2. **沉默不是通过**:没量过 = 判死。`judge(None)` 一律 DEAD,
   不造零、不造真(M69c / H6c / L4–L6 同律)。
3. **检查器必须先证明自己查得出**:证明的办法是**喂合成缺陷**,
   不是等现实里出问题(变异闸门 290 项的全部理由)。
4. **数字只出自一个脚本**:`gate_report.py`;散文只解释不下判断。
5. **测试模式体系(九模式)**:每批预注册必须声明 `test_mode`。
   混称会导致两类错误 —— 拿开发期任务谈能力(过拟合)、
   拿判据攻击实验谈成功率。**T1–T3 是开发套件,不是 held-out。**

### 4.3 出题的两道闸(本线最可复用的产物)

任务必须**同时**通过:
- **H6 欠定闸**(题面信息不足 → 模型无从做对,不是能力问题);
- **0.95 盲攻线**(题面信息过剩 → 不读隐藏 oracle 也能做对,测不到东西)。

盲攻 = 独立攻击者(与出题方无涉)只读交付树 + 题面,不读隐藏 oracle、
不读原实现、不跑测试、不迭代、单发。ratio = 攻击后 delta 转绿数 / delta 集大小。

**分母薄的代价**:delta 集只有 1 个节点时,ratio 只能是 0% 或 100%
——准入分辨率是 1 bit。这个性质必须**在开打前**记入协议,不能事后解释。

### 4.4 泄漏扫描的实测教训

扫描面必须是**攻击前**交给攻击者的那份树。封存池里 `attacks/<cid>/delivery`
是**攻击后**的树 —— 拿它当扫描面,会把"攻击者独立想到了同一个函数名"
读成"答案泄漏"(click-3581 实测:攻击后树命中 3 处,而该发比分 0/3,
攻击者根本没做对)。

### 4.5 环境与封存纪律(踩过的坑)

- **封存不重下**:封存件永不重新下载;缺依赖时用**多个封存轮仓拼装**
  (`--find-links` 可重复给)。实测:more-itertools 需 click 的 setuptools;
  pluggy 需 setuptools + sqlglot 的 setuptools_scm + `SETUPTOOLS_SCM_PRETEND_VERSION`;
- **摘要绊线是会响的**:Finder 往封存 runtime 根落一个 `.DS_Store`,
  `verify_sealed` 当场拒开(闸门按设计工作,不是误报);
- **老树装不上新 pytest**:click-3533/3582 因 `filterwarnings=["error"]` +
  仅有 pytest 9.1.1 而收集期崩 —— 这是**供给受限**,不是任务缺陷。

### 4.6 仪器教训

早期 3 发无用量记录;DSH 回执面曾误报"无 budget_refused"——
**仪器缺失会被读成"现象不存在"**。凡结论依赖"没看到 X",
先确认量具**量得到** X。

## 5. 未关闭的问题(重走时的待办)

1. **P3 稳定性复测(编排已就绪,未执行)**:4 组合(3581-v2 / 8042-v2 ×
   gpt-5.5 / 5.6)× n=3 = 12 发。预算按实测推:≈ **4.6M 名义 in / 130K out /
   顺序约 2.5 小时**(cache 折后实际远低)。
   判定线:3/3 = 稳定过;2/3 = 不稳定,失败样本入修复线;≤1/3 = 推翻。
2. **v3 delta 口径(未裁决)**:是否把 delta 从"PR 新增测试函数"放宽为
   "**红→绿翻转节点集**"(不论节点新旧)。
   - 供给面:**完全离线可做** —— 窗口 2 的 7 个电池死者 + 窗口 1 死于口径的
     6 个 ≈ **12 个候选可直接重裁**(题面都在手,无需新窗口);
   - 三个待裁设计点:① 最低翻转节点数(实测这批**全部只有 1 个**,
     要求 ≥2 即全杀);② 改既有测试型要整文件移除测试件(公共回归面大损),
     fixture 型损失小 —— 是否区别对待;③ 0.95 线沿用与否。
3. **DSH 预算轴**(§3.5)—— 三者不相容,需重新设计而非调参。
4. **T2/T3 稳定性差距的模型侧**(§3.1)—— 前三层已修待验。
