# 评审独立性:现状取证与整改规划

**触发**(2026-08-12,用户提问原文):

> 是否当前的测试修改和项目修改效果评判以及结果声明都是一个 agent(你)做的?
> 我觉得修改和评价修改结果都有同一个 agent 容易自话自说,需要更准确和科学的
> 测设-修改-评测-再修改直到结束的流程。

本文是取证式回答 + 规划。**不含承诺性措辞**:每条现状都给出可复跑的证据,
每条规划都给出交付物、判据、成本与验收人。

---

## 1. 短答

分三层看,答案不一样:

| 层 | 内容 | 修改者 | 评判者 | 是否自话自说 |
|---|---|---|---|---|
| L1 | **被测模型**把开源能力适配进宿主 | 外部模型(沙箱) | 确定性 oracle 程序 | **否**(结构性隔离) |
| L2 | **harness / 任务 / oracle / 归因** | 我 | 我 | **是** |
| L3 | **对用户的结论声明** | 我 | 无 | **是,且无任何拦截** |

所以:**benchmark 的 5 个真实 PASS 不是我判的**(L1 的隔离是硬的,见 §2.1);
但**"harness 是对的""这个失败该算谁的""闸门达到了"这些结论全是我一个人
出题、一个人改、一个人判、一个人宣布**——你的直觉在 L2/L3 上完全成立,
而且有五起实证。

---

## 2. 现状取证

### 2.1 L1 已经分离(不要连带怀疑它)

被测 agent 与评判之间的隔离是结构性的,不靠自觉:
`network=none` + `offline=True` + `NO_PROXY="*"` + 假 HOME;agent profile
拒绝 oracle 与 harness 源码;唯一的人机通道是 scope-change 暂停,而 5 发
PASS 全部 `scope_change=0` / `rollback=0` / `replay=PASS` /
`main_dir_integrity=ok`;trace 哈希链 + `trace_sha256` 入台账。
判 PASS/FAIL 的是 pytest + junit + 干净重放,**不是一个当裁判的 LLM**。

### 2.2 L2:七个角色我占六个

| 角色 | 当前承担者 | 独立? | 证据 |
|---|---|---|---|
| 出题(契约 + oracle) | 我 | 否 | `benchmarks/v2/tasks/*` 全部我写 |
| 实现(被测适配) | 外部模型,沙箱 | **是** | §2.1 |
| 能力评测(执行) | 确定性程序 | **部分** | 执行独立,**判据作者仍是我** |
| 失败归因 | 我 | 否 | 今天这次提交本身:`replay infrastructure failure` 这个标签我写的,判它写错了的也是我 |
| 自查判据(钉死测试) | 我,**且与实现同一次提交** | 否 | 144 次提交中 **69 次**同一 commit 里既改 `src/` 又改 `tests/`;另有 **11 次**只改 `src/` 不动 `tests/`(`git log` 可复算) |
| 结论声明(台账/日志/对你说的话) | 我 | 否 | §2.4 |
| 验收(宣布"闸门达成") | 我 | 否 | 无第二方签收 |

`69/144` 这个数字是关键:**判据与被判对象在同一时刻由同一人写出**,
判据几乎不可能不"恰好"通过——它是照着已完成的实现写的。

### 2.3 缺陷发现渠道分布(最近 5 起完整性缺陷)

| 缺陷 | 发现方式 | 存活时间 |
|---|---|---|
| #26 裁定不进台账 → 台账自失真 | 自查(四阶段收官定期核对) | — |
| #27 探索性加发无归属标 | 自查(建 UI 时顺手) | 未发生 |
| #29 前缀白名单放行了装着答案卷的 T4 栈 | **偶然**(查 T3 阻塞时撞见) | 约 1 天 |
| #30 冒烟发被计入闸门通过数 | **用户质疑** | **3 天**(08-09 → 08-12) |
| #31 归因反了(harness 替模型认领错) | 自查(在你要求分析失败原因时) | 约 15 小时 |

自查确实有效(3/5),但**两起"方向反了"的闸门缺陷都不是流程抓到的**:
一起靠撞见,一起靠你。这正是"自己审自己"的典型失效形态——不是不认真,
是**看不见自己的盲区**。

### 2.4 反例最有说服力:机制已经存在,只是没盖到出错的地方

`scripts/check_public_claims.py`(Gate 8A.3,零 LLM、确定性、非零退出)
的设计正是"散文声明必须与机器事实源一致"。**它今天仍然全绿**——因为
V2 宿主闸门的数字根本不在它的事实源里:`docs/benchmark_summary.json`
全文零 `offerclaw`,而 T1/T2/T3 的通过数只以**手打散文**形式活在
`docs/LESSONS_LOG.md` 与批报告里。

⇒ 我们不缺"确定性校验"这个范式,缺的是把它铺到 L2/L3。

## 3. 诚实的边界:哪些"独立"是假的

1. **我编排的任何审查 agent**:模型是我选的、提示是我写的、输出是我读的、
   采纳与否是我定的。它独立于**上下文**,不独立于**我**。价值真实但有限。
2. **LLM 审查者不是 oracle**。它的漏报率必须被测量,否则只是多了一层
   看起来很像审查的东西(见 §4-D2)。
3. **真正的外部只有三个**:①事前冻结的确定性判据(它在我改代码之前
   就写死了,我事后无法讨价还价);②你;③你招募的外部审查者——仓库
   已转 public,这条路已经打开。

---

## 4. 四道独立性来源(按强度排序)

- **D1 事前冻结的机器判据**——最强、最便宜。核心不是"有测试",是
  **判据的冻结时刻早于实现**,且冻结物不可事后改写。
- **D2 变异语料(评测者的评测者)**——把"我测过了"变成一个可复算的数字:
  已知缺陷注回代码,套件抓不抓得到?捕获率就是我的自查能力的实测值。
- **D3 异构模型对抗复核**——干净上下文、只看 diff 与声明、提示词是**证伪**。
  独立于上下文。
- **D4 你 / 外部审查者**——唯一的真外部。稀缺资源,只花在 D1–D3 消化不了
  的判断上(取舍、优先级、可接受风险)。

### P2 · 结构性

7. **CI(仓库已 public,GitHub Actions 免费)**
   每次 push 跑:全量套件 + claims 一致性 + 变异闸门 + 红-绿留痕检查。
   **由机器宣布通过,不由我的散文宣布**;外部审查者能直接看到红绿。
8. **角色分离到人**:批次结论由你签收;我只产出证据包,不写"闸门达成"。

   读法成立**(CONTRACT_UNDERSPECIFICATION 的上位形态)。

## 6. 环路定义(测设 → 修改 → 评测 → 再修改 → 结束)

| # | 步骤 | 产物 | 门 | 谁 |
|---|---|---|---|---|
| 0 | **测设**:写下"什么现象算修好了"+ 一条反例,冻结 | commit 判据段 | 判据不可事后改写 | 我 |
| 1 | **红**:钉死在未修复代码上跑,必须 FAIL | `redgreen/<commit>.txt` | 无红即无效 | 机器 |
| 2 | **改**:最小实现 | diff | — | 我 |
| 3 | **绿**:钉死过 + 全量回归 + 变异闸门 + claims 一致 | 套件输出 | 任一红即回步骤 2 | 机器 |
| 4 | **复核**:异构 agent 证伪 | `reviews/<commit>.json` | 未消解反对 = 阻断 | 异构模型 |
| 5 | **声明**:数字由脚本生成,散文只解释不下判断 | 报告 | 散文与 json 不一致即红 | 机器 |
| 6 | **收**:批次结论签收 | 签收记录 | 未签收不得对外声明 | **你** |

"再修改直到结束"的**终止条件**必须是机器可判的:步骤 3、4、5 全绿且
步骤 0 的反例仍然被抓住。**不允许以"我认为可以了"结束。**

## 7. 这个流程本身也要被度量

否则它会变成一套更精致的自话自说。每月统计四个数:

1. **缺陷发现渠道分布**(自查 / 流程门 / 偶然 / 用户 / 外部审查);
2. **变异捕获率**(§5-5);
3. **红-绿留痕覆盖率**(有红证据的钉死 / 全部新增钉死);
4. **我的散文声明与脚本产出不一致的次数**。

**判据**:三个月后若"用户发现"仍稳居前二,说明流程没起作用,推倒重来。
当前基线(§2.3):自查 3 / 偶然 1 / 用户 1,变异捕获率**未测**,
红-绿留痕覆盖率 **0%**。

**2026-08-12 更新(P0-1/2/3 与 P1-5 落地当日)**:变异捕获率 **13/13**
(首跑,含金丝雀自证);红-绿留痕覆盖率:归因修复的 6 个钉死已补做
(base 全红 / fix 全绿),**此前所有历史钉死仍无红证据**——只对新修复
强制,不给历史伪造证据。缺陷发现渠道新增一例:**流程门 1**(变异闸门
基线运行抓到位置敏感钉死,LESSONS #32)——这是"流程门"渠道的第一次
开张,正是本规划要把发现渠道从"偶然/用户"搬过来的方向。
