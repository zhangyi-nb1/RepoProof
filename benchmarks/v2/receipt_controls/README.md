# 上游执行回执的零模型正负控(第 6 步)

回答一个问题:**这套回执,到底伪造得了伪造不了。**

全程不调用任何模型。sidecar 是真进程,上游是真包(`markdown-it-py`),
渲染是真执行,回执是真签名。所以结论不依赖任何模型的表现 —— 不会被"这次
模型比较笨"或"这次模型特别会钻空子"污染。

```bash
.venv/bin/python scripts/verify_receipt_controls.py
```

**nc3 是这套设计真正的考题**,也是唯一**只红在 U4** 的一条:U1/U2/U3 全绿
—— 真上游确实被真的调用过,输入摘要也对得上。任何"记录调用发生过"式的回执
都会给它发绿。它证明四道谓词的分工是真的,不是四个名字挂在同一个布尔上。

## 四条判定纪律

1. **正控必须全过**。一道诚实实现也过不了的判据不是判据,是墙。正控刻意做
   了无害的后处理(去行尾空格、补尾随换行),判据必须容得下 —— 容不下就是
   误杀,和放过洗白一样坏。
2. **每个负控红在它自己那一处**,期望集与实际集**逐一相等**。红一片不算数。
3. **脚本先自证**:把采纳谓词换成"永远放行",nc3 必须由 FAIL 变 PASS。不做
   这步,"八个负控全被抓住"分不清是验证器真抓住了,还是脚本在读自己的期望值。
4. **每族谓词都得红过也绿过**。全红的判据与"恒红"无从区分(不携带信息),
   从不红的判据则根本没被这批负控考到 —— 两种都当场说出来。

## 两处方法论修正(记下来防再犯)

**nc5 一开始没在考它声称要考的东西。** 密钥每 run 现摇,重放的旧账在
`U1.signature` 就先挂了,`U1.run_nonce` 那道根本走不到 —— 这条负控实际考的
是密钥轮换。改成**沿用上一轮的密钥**才把 nonce 单独拎出来:签名完全有效、
链完整、内容真实,唯一不对的是它不属于这一次运行。与 M46a 同型的错误:
考的是代码顺带处理的情形,不是判据真正管的情形。

**`U1.signature` 一开始没有任何负控让它红。** 加 nc8 补上,并且刻意做成最强
的伪造者 —— 给它台账路径、让它把 `prev_sha256` 算对、身份与摘要全填对,唯独
签不出名。它与 nc5 是一对:nc5 签名有效而 nonce 不对,nc8 nonce 对而签名无效。
两条合起来才说明这两道各自都在干活,而不是其中一道替另一道背了书。

## 本批没考到的子判据(如实列出)

`U1.chain` · `U1.invocation_unique` · `U1.version` · `U2.upstream_identity`

四条都有单元钉死覆盖(见 `tests/test_upstream_receipt.py`),所以是**分工
问题不是缺口**。其中 `U2.upstream_identity` 值得单说:要在本矩阵里考它,得让
**sidecar 自己**去加载假包 —— 而 sidecar 是 harness 拥有的,不在本轮威胁模型
内。将来若 Runtime Profile 允许第三方提供执行器,这条就得进矩阵。

## 边界

- 上游选 `markdown-it-py` 而非 `browser-use`:后者在钉版离线环境里根本导入
  不了(见 `docs/EXECUTOR-UPGRADE-PLAN.md` §4.1)。本矩阵证明的是**回执机制**
  的不可伪造性,与具体上游无关。
- 采纳谓词用 `text/whitespace-squashed` 口径。口径选松了这条判据会退化成
  "搬运即可满足" —— 那是任务的责任,不是回执机制能替它决定的。
- 本矩阵不涉及任何模型发次,不进 `runs.jsonl`,不影响任何闸门数字。
