## 0. 为什么 D4 卡了三周,以及它是怎么解开的

D4 的记法是"WH 的 H0/H2 全仓无定义"。查盘后真正的卡点不是没写字,是
**方案文档 §7.2 的 H2 由六件不存在的部件拼成**:

| §7.2 列的 H2 部件 | 盘上实况 |
|---|---|
| E1 Context Projection | 建了。批 14/15 两批消融后 **A2 否决,对 GPT 代际归档关闭**(默认 off) |
| Persistent State(S3) | **从未建** —— 基线 `cd` 共 1 条、重复命令 0,判 `NO_EXPOSURE` |
| Editor(S4) | **从未建** —— 语法错误 0、权限 0,判 `NO_EXPOSURE` |
| Contract Capsule(S5) | **从未建** —— 判 `BLOCKED_BY_INVALID_CONSTRUCT` |
| Requirement State(S5) | **从未建** —— 状态板会**主动给错误正信号**(order-68 交假包却 24/24 全绿,板子会标 `EVIDENCED`)|
| FailurePacket v2 | FailurePacket 在(RFC-006,含 SHARED_ROOT_CAUSE/TIMEOUT/ROLLBACK);是否算"v2"无定义 |
| Best State | 在(`best_state` + 硬信号退步才回滚) |
| Targeted Public Tests / Context Reset | **无对应实现** |

照那张清单实现 = 为一次消融**临时造六个没有独立证据的机制**,与"先冻结
判据、再测"正相反,也违反 §39(不为了通过率造机制)。

**解法:两臂按盘上真有的东西定义**,差集恰好是 harness 今天所谓"引导"
的全部。定义已是代码(`src/repoproof/runner/host_guided.py`,三个纯函数
`harness_mode` / `effective_budgets` / `round_guidance`),钉死
`tests/test_wh_harness_modes.py` W1–W5,变异 M80a–e:

| | H2 = `guided`(默认) | H0 = `minimal` |
|---|---|---|
| 轮编排 | 多轮(契约 `max_rounds`) | **单轮** |
| 轮间反馈 | 结构化 FailurePacket(公开测试 / 宿主回归 / 策略·预算·依赖违规) | **无**(agent 自己跑测试,读原始输出) |
| 最佳态 | 硬信号退步则 git 回滚到最佳提交 | **无**(单轮,自然不适用) |
| 轮抬头 | 讲修复轮 + 回滚 + scope-change 协议 | **只留安全句**"不许编造测试结果" |
| 总额度 | 每轮 × 轮数 | **同一个总和,一次给足**(W2 钉死) |
| 交付物上限 / 墙钟 | 契约值 | **同一条线,不放宽**(W3 钉死) |
| 安全面 | 策略执法、预算硬墙、越界拒绝、六层终局验证、干净重放 | **逐字相同** |

**为什么安全面必须相同**:摘了安全的那臂若输,赢的可能只是"没被允许
撒谎/越界",测出来的是安全网的价值,不是引导增益。

**两臂不混池**:三面指纹分离,代际标签记 `E0-H0`(单列后缀,不进 steps
—— 最小臂是**减配**,写成 `E1-H0` 读起来像加了一步,正好反了)。

## 2. 任务池与它的硬限制(如实,决定了本批只能是 pilot)

方案文档 §7.3 的最小规模是 **3 个未见任务**。盘上未见任务池 = HB 三题,
逐题核可用性:

| 任务 | 有无"可解"证据 | 本批可用性 |
|---|---|---|
| sqlglot-8042 | **有** —— gpt-5.5 / gpt-5.6 各 1 发 PASS_ADAPTED(delta 5/5) | ✅ 唯一有实测天花板余量的题 |
| click-3581 | 无 —— 两 GPT 双双 0/3(= 盲攻上界) | ❌ 地板锁死,两臂都只能是 0 |
| click-3407 | 无 —— 两 GPT 双双 0/1 | ❌ 同上,且本身是 1 bit 单薄档 |

**结论:池子只支撑 1 题,不是 3 题。** 故本批显式记为 **pilot,低于
方案文档最小规模**,其 null 结论**不足以支持"harness 无增益"**(§6 停
止规则据此写)。

**另一条结构性限制(必须写在前面)**:§7.5 的增益判据二("至少两个任务
上产生稳定 Public Test 正向增量")在 HB 任务族上**不可测** —— HB 的公开
面按 HB 预注册 §4 裁决 A 是宿主回归套件,而它**基线即全绿**,没有正向
增量的余地;delta 测试全程隐藏,终局才判。所以本批只有判据一可用,并
补一条更细粒度的连续读数(§4)。

## 4. 结局量(先写死,发完照此读)

| 量 | 定义 | 地位 |
|---|---|---|
| 有效 PASS | 沿 harness 现行词表(delta 全绿 ∧ 回归零破坏 ∧ 干净重放一致) | **主结局**(§7.5 判据一) |
| delta 节点数 | 终局隐藏 oracle 的绿节点数,0–5 | **次结局**:PASS 之下唯一的连续读数;两臂 0 vs 0 与 0 vs 3 是完全不同的结果 |
| 是否提交 | J3 = `NO_SUBMISSION` 与否 | 过程观察 —— DeepSeek 两发实测均打满 30 调用未提交,这正是引导可能起作用的地方 |
| 回归破坏 / 策略违规 / 假 PASS / 泄漏 | 逐发计数 | **护栏**(§7.5 同时必须满足:三者不增、泄漏恒 0) |

**引用纪律**:任何 delta 读数必须与该题**盲攻上界 4/5** 并排出现。

## 5. 增益判据(冻结措辞)

- **判据一(主)**:H2 比 H0 多 ≥1 个有效 PASS → 判 `GAIN`;
- **判据二(次,本批替代方案文档那条不可测的)**:两臂 delta 节点数的
  逐发读数,H2 严格优于 H0 且**至少 2/3 发成立** → 判 `WEAK_GAIN`;
- 两条都不成立 → 判 **`NO_GAIN_IN_PILOT`**,措辞**不得**写成"harness
  无增益"(样本 n=3、单题、低于最小规模);
- **反向**:若 H0 严格优于 H2 且 ≥2/3 发成立 → 判 `ADVERSE`,按批 15
  S2′ 的处置办法处理(记录 + 不外推 + 机制不升默认);
- 上述任一判决都必须同时满足护栏(假 PASS 不增、回归破坏不增、策略
  违规不增、隐藏泄漏 = 0),否则整批判 `INVALID`。

## 6. 停止规则

1. 任一发出现隐藏 oracle 泄漏 → **整批作废**,重预注册;
2. 批期间发现判据缺陷 → 停批线 4(同 HB 预注册):当批作废重来;
3. 批期间发现**量具**缺陷(非判据)→ 停跑 → 钉死 + 附录 → 复测 → 该发
   从零重跑,已跑发次不改判(与 HB-PCDELTA-1 首发中止同一条处置);
4. 连续 2 发 `HARNESS_FAILURE` → 停批查因(`SUITE_TIMEOUT` 不入此计数,
   理由见 HB 预注册附录一);
5. **null 的记法**:`NO_GAIN_IN_PILOT` 必须连同"池子只支撑 1 题"一起
   写进批报,不许单独引用。

## 附录二 · 分类旁挂预写(§8.5;**落笔于任何计分发次之前**)

6 发计分发次的旁挂字段在此定死,发后只填 `run_id`/`run_order`/`notes`
(实测读数)。`classification_timing=PRE_REGISTERED` 的凭据就是本附录 ——
run_id 是时间戳,开跑前无从预知,故预写的是**取值**不是行。

```json
{
  "test_mode": "WH",
  "run_purpose": "MECHANISM_ABLATION",
  "task_seen": false,
  "counts_toward_model_capability": false,
  "counts_toward_heldout_benchmark": false,
  "counts_toward_mechanism_effect": true,
  "counts_toward_treatment_effect": true,
  "treatment_assigned":  "guided → true,  minimal → false",
  "treatment_activated": "guided → true,  minimal → false",
  "exclusion_reason": "MECHANISM_ABLATION_NOT_CAPABILITY",
  "assistance_level": "guided → BOUNDED_PUBLIC_REPAIR,
                       minimal → SELF_SERVE_PUBLIC_SINGLE_PASS",
  "oracle_authorship": "UPSTREAM_OWN_TEST_SUITE",
  "host_modification_mode": "PRISTINE",
  "classification_timing": "PRE_REGISTERED",
  "classified_at": "2026-08-17"
}
```

三处取值与既有批次不同,理由必须写在前面:

1. **`exclusion_reason` 是新值,不沿用 `SEEN_DEVELOPMENT_TASK`** —— E1 那批
   排除能力口径是因为跑在开发套件上,而 sqlglot-8042 是**未见**任务
   (`task_seen=false`)。本批排除的真理由是**它测机制不测能力**。沿用旧值
   等于在台账里写一条假理由,而假理由日后会被当成真的引用。

2. **两臂 `assistance_level` 必须不同名** —— 引导臂是 harness 中介的多轮
   修复(`BOUNDED_PUBLIC_REPAIR`),最小臂没有任何 harness 中介反馈:
   公开面照给,agent 自己跑自己读,一轮走完
   (`SELF_SERVE_PUBLIC_SINGLE_PASS`)。两臂记成同一个词,台账就丢掉了
   **本批唯一在测的那个区别**。两值都非空,故两臂都照常计入
   `assisted_repair_runs` —— 相对盲攻,拿到公开测试套件本身就是协助。

3. **`counts_toward_heldout_benchmark=false`,尽管 oracle 确是上游自带**。
   如实记 `oracle_authorship=UPSTREAM_OWN_TEST_SUITE`(事实就是如此),
   但严口径闸门的第二道由本字段独立关闭:WH 发次是机制消融,最小臂更是
   **减配构型**,它的失败说不出模型能力的任何事。混进 held-out 台账会污染
   K6/K12 的 8/2。

预注册文档,**执行路径逐字节相同**。故首发验的是与后 7 发、与 6 发计分
发次完全同一条代码路径。

记在这里而不是补跑一发:补跑会让电池变成 9 发、四形态里有一形态重复,
自证脚本的"两臂各四形态"归位检查就得跟着松口 —— 为了让记录好看而放松
检查,方向正好反了。

## 附录四 · 开跑前的一处判据修补(2026-08-17,**仍在任何计分发次之前**)

拿 F0 电池已落的两发试跑判据脚本时,顺手核了它的池划分,发现两件事,
都在计分发次之前修掉:

**一、计分池 / 自证池的分界线失败方向朝松**。原写法是
`model.startswith("fake")`,判别名换个写法(`scripted-fake:`、大写
`FAKE-`)就漏。两个方向的代价严重不对称:

| 误判方向 | 后果 | 会不会响 |
|---|---|---|
| 假发次漏进**计分池** | 脚本 fake-positive 直接造出假 GAIN,它和真 PASS 长得一模一样 | **不响** |
| 真发次误进自证池 | 两臂发次数不等 → INVALID | 当场响 |

故改为子串命中(`"fake" in m or "scripted" in m`),**宁宽勿窄**。

**二、同一个谓词抄了三份**(计分池、自证池、`--f0-batch` 路)。这是
usage 回调那次的同型病:改其中一份,另两份静默走旧语义,而"哪份被走到"
取决于命令行参数。收成一份 `is_smoke_model`,并**钉实现份数而非某处行为**。

**三、缺 `model` 的台账行原先默默进计分池** —— 计分要它是真模型,自证要
它是脚本,而这行两样都说不出;归入任一池都是替它编一个身份。改为抛错。

钉:X8 两条(失败方向 + 一份实现);变异 M81g(退回前缀匹配)/
M81h(缺 model 默默计分)。注册表 233 → **235**。

**为什么这算合规**:改动全部落在第一发计分发次**之前**,且判据的判决语义
(§5 五支)一字未动 —— 改的是"哪些发次进得了判据",不是"进来之后怎么判"。
若同样的缺陷在开跑后才发现,走的是 §6 停止规则三(停跑 → 钉死 → 附录 →
该发从零重跑),不是就地改。

## 附录五 · 泄漏护栏由声明改为重验(2026-08-17,**仍在任何计分发次之前**)

通读 `judge_arms` 时发现:§5 列的四条护栏,判据脚本只实现了三条。
**"隐藏泄漏 = 0"没有对应代码。**

原因不是疏忽,是它与另外三条形态不同:另外三条是逐发读数(假 PASS、回归
破坏、策略违规),泄漏则是**建包时的结构性事实** —— 交付树里有没有答案
指纹,与某一发怎么跑无关。证据一直在
(`docs/evidence/hb1_hosts/prepare-hb1.json` 的 `leak` 段:45 枚有效指纹、
`hits: []`、`planted_detected: true` = 扫描器自证有牙)。

但"证据在盘上"和"出判决时验过"是两回事。躺在 json 里没人重读的结论,
就是散文承诺 —— 而这一批的整套纪律正是"结论由机器判,不由散文判"。

故补 `leak_guardrail()`,**每次出判决时重验两件**:

1. 建包扫描结论,且**扫描器自证有牙**(种植件报中、干净树零命中)——
   拔光牙的扫描器同样报"零命中",不验自证等于采信一个可能没牙的结论;
2. 部署树**至今逐字节未变**(复用 `blind_attack_admission._digest_tree`
   原件量法,不重算一份 —— M58a 钉的就是复制品静默漂移)。否则那份泄漏
   结论说的是另一棵树。

接线方式:`judge_arms` 加 `extra_breaches` 参数,**纯函数不为它开后门**
—— 泄漏破了照样先于增益判,与另外三条同级。认不出的任务一律报"无从重验"
而非"干净":没证据 ≠ 有证据说没有。

实测当前盘上:`hits=0 / effective=45 / clean_zero / planted_detected /
selfcheck_ok / digest_match` 全绿。

钉 X9 三条(重验痕迹 / 未知任务不读成干净 / 泄漏先于增益);
变异 M81i(护栏传进来不参与判决)、M81j(未知任务读成干净)。
注册表 235 → **237**。

## 附录六 · D9:批封套由 3.0M 抬到 12M(2026-08-17,**仍在任何计分发次之前**)

### 缺陷

§7 写的批封套"读入 ≤ 3.0M"是在**把两臂额度换算套到这份契约之前**定的。
套上去之后,数字对不上:

| 额度(hb1_sqlglot_8042,`semantics=per_round`) | 契约 | guided | minimal |
|---|---|---|---|
| max_rounds | 3 | 3 | **1** |
| max_model_calls | 30 | 30 | **90** |
| max_commands | 100 | 100 | **300** |
| max_input_tokens_total | 600K | 600K | **1.8M** |
| max_output_tokens_total | 80K | 80K | **240K** |
| max_patch_files / max_patch_lines | 15 / 1500 | 15 / 1500 | **15 / 1500** |
| max_wall_time_minutes | 60 | 60 | **60** |

**顺带得一条实证**:两臂读入总额确实相等 —— guided 600K×3 轮 = 1.8M,
minimal 单轮 1.8M。交付物上限与墙钟两臂同线(W3 钉的就是这条,此处是它
在真契约上的落值)。等总额设计站得住,不是纸面声明。

### 基数从哪来(不是拍的)

| 来源 | 每调用读入 |
|---|---|
| deepseek-v4-pro × sqlglot-8042 两发(HB-DSENTRY-1) | 19.0K / 26.9K |
| 去重修复**之后**的 E1-S2PRIME 六发(gpt-5.6,另一任务) | 18.7K – 33.0K |

两组同量级 ⇒ 这批历史数**不是台账虚高的产物**,可作基数。取 ~25K/调用。

### 投影

- guided:历史打满 30 调用即止,0.57–0.81M/发 → **~2.1M**;
- minimal:90 调用 × ~25K ≈ 2.2M > 1.8M 硬墙 ⇒ **撞墙,1.8M/发** → **~5.4M**;
- 批合计 **~7.5M**,绝对上限 6 × 1.8M = **10.8M**。

3.0M 差 2.5–3.6 倍,不是能省出来的量级。

### 裁决(用户 2026-08-17)

**批封套读入上限 3.0M → 12M**(= 绝对上限 10.8M + 余量)。产出、墙钟、
运行数三项**不动**。

**不变的东西**:D6 的 n=3、两臂各 3 发、执行序 ABABAB、§5 五支判据、
判据二的 2/3 线 —— 一字未改。改的只是花多少钱的上限。

**为什么这不是事后放宽**:①落笔在第一发计分发次之前;②封套是**开销闸**
不是判据,§5 五支判决没有一支读它,§6 停止规则也没有一条以它为触发;
③替代方案(n 降到 1)会让判据二退化成单一对子决判 —— 那才是真正在动
判据。

**若开跑后才发现封套不够**:走 §6 停止规则,当批停,重预注册 —— 不在批
中途抬。这条写在这里,是为了让"什么时候可以改、什么时候不可以"有个白纸
黑字的分界,而不是每次临时讲道理。
